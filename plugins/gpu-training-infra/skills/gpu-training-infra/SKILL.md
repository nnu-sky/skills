# 模型与计算工程优化

## 目标与范围

面向模型及相关计算流程开展性能优化，覆盖训练、推理、评价、模拟、数值计算以及数据和系统执行。根据用户目标决定真实工作负载、关键指标和改动边界，不默认训练优先，也不预设特定硬件或技术方案。

允许工程执行改进、数学等价改写、表示和计算重组、成熟成果复用，以及任务容差和授权范围内的精度调整、近似或替代算法。默认代表性短测与必要的正确性信号；随机种子沿用项目协议，无协议时使用 3407。完整训练、多种子和大规模搜索仅按任务需要开展。

## 初步判断与优先级

结合源码、实际执行入口、已有日志和轻量基线，从四个方向寻找优化机会：

1. **执行与硬件适配**：数据供给、传输、通信、内存、并行、调度、编译、算子和硬件执行。
2. **数学与计算重组**：代数化简、数值实现、依赖重排、重复计算消除、状态复用、融合和计算表示。
3. **成熟技术与成果复用**：论文方法、开源实现、数学库、框架后端、编译器和硬件厂商方案。
4. **算法与流程创新**：替代算法、复杂度改进、新数据结构、增量计算、新执行机制与跨阶段重构。

这些方向用于发现机会而非限定研究范围；无需逐项尝试。综合运行占比、调用频率、结构性改进空间、预期收益、实现成本和用户目标选取候选。结合时间证据和输出、梯度、状态依赖判断真实必要计算，未测量的机会标为假设。

## 常规优化与深度研究

**常规工程模式**优先采用低成本、机制明确、能够较快验证的改动与成熟实现，持续交付可靠的效率收益。

**深度研究模式**从数学、算法、表示、计算依赖、编译、硬件执行及系统流程出发，研究计算方式本身能否重组或替代；结合相关工作、独立候选和局部原型寻找更有价值的优化机制。允许成熟技术组合、原有机制改进或新方法，不以新算子作为深度标准。

两种模式的界限取决于目标和研究方式，而非技术难度或加速倍数：常规模式优先解决已定位问题、交付可靠收益；深度模式主动质疑原始计算方式，并根据实验反馈持续更新研究假设。常规模式发现需要大量探索的候选时可以记录并按用户目标决定是否扩展研究，不擅自扩大资源投入。

两种模式可独立或并行推进。用户明确要求深入研究、系统探索或论文创新时可直接进入深度研究，无需等待全部常规优化完成，同时建立适当的成熟强基线。深度模式参考 [深度计算优化研究](references/deep-optimization-research.md)，不强制候选数量、研究轮数或方法清单。

用户明确限定方向、原实现或授权时遵守边界。涉及训练目标、方法含义或资源投入的实质改变时让用户决定；可独立的工作继续。将研究原型与已验证的可用实现分别记录。

## 迭代执行

已读规则、手册和仍适用的优化记录直接复用。参考资料仅在需要时读取相关部分；环境变化时复查受影响的条件。

1. 按 [基线与定位](references/baseline-and-profiling.md) 确认实际执行周期、目标使用长度、资源、允许改动范围和正确性要求，完成四方向初扫与轻量基线，核对主要环节的测量范围。
2. 按 [优化手册](references/optimization-playbook.md) 为优先候选明确：哪段计算或等待可能有浪费、作用机制是什么、用什么最小实验判断。
3. 实现候选并短测，依据 [验证与结果说明](references/acceptance-and-reporting.md) 判断速度、资源和正确性。有效改动进入当前组合，失败候选回退或记录适用条件。
4. 以当前组合重测代表性执行全链，检查剩余开销与瓶颈迁移，按任务目标和所选模式判断继续或收束。收益有限时，区分候选占时小、实现未奏效与测量不具代表性，再决定投入。相关候选有强交互时可测试小型组合，再做必要的拆分。
5. 深度研究参考 [深度计算优化研究](references/deep-optimization-research.md)，按实际问题开展相关工作、机制探索及原型实验。
6. 涉及批量变化时参考 [批量与成本评估](references/batch-size-and-cost.md)，将训练配方变化与纯工程收益分开说明。

在项目的 `research_log.md` 简要记录假设、结果或失败现象、原因判断、修改和保留决定，复用已有记录形式。已有分析中提出的候选也进入记录，逐项标明已验证、待短测或暂缓理由，优先处理仍有依据的重要候选。用户补充方向或询问进度时，合并到当前任务并在回答后继续已授权工作。阶段实验后回到本任务目标，判断现有证据是否足以回答问题；目标尚未达到且范围内仍有值得投入的候选时，继续实际执行。

## 按需委派与工作树

主代理直接完成快速查询、小范围检查和简单推导。复杂且相对独立的调研、数学分析、模块审查和原型实验，可在可用能力支持时并行委派。比较并行收益与启动、交接、协调成本，动态选择适当数量与分工，不为并行而并行。

并行任务明确研究问题、基准版本、输出和边界；主代理继续不依赖分支结果的工作。需要同时修改同一仓库时，优先建立独立 Git worktree 和分支，隔离代码及实验输出，不覆盖用户已有未提交变更。工作树不隔离 GPU 和外部绝对路径；共享硬件的正式性能测量需避免资源争用。

主代理比较候选、处理依赖和合并冲突、择优整合有效实现。简单任务或强依赖任务不强制开启工作树；实验分支未经验证不直接替换交付版本。

## 完成与交付

达到用户目标，或当前范围内的重要候选已处理、剩余机会缺乏机制依据或预期收益不足以支持投入时，完成当前最佳组合的必要检查并交付。正在运行的正式训练与独立优化副本分别处理：在已有授权和可用资源内继续副本实验，将验证通过与实际切换运行分别报告。必要验证超出已有资源范围、存在必须由用户决定的方法变化或外部阻塞时，报告已完成部分和具体待决事项，继续可独立推进的工作。

停止时简要说明未采用的重要候选及理由，无需穷尽所有技术。报告原始情况、实际改动、单项与组合收益、显存、正确性信号和适用条件。收益声明与测量范围一致：区分局部算子、目标阶段、稳定执行窗口和完整工作负载。当前没有可证实的收益也是有效结论。
