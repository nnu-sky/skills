# 诊断流程

## 顺序

1. 确认主机、账号、默认路由和基础 DNS。
2. 确认 Mihomo 服务以及 HTTP、SOCKS、控制器监听。
3. 检查进程实际继承的代理环境变量。
4. 对目标执行一次直连和一次显式代理请求。
5. 查询两个节点提供器的类型、节点数、更新时间，并区分“订阅非空”和“节点业务健康”。
6. 查询七个业务组和两个第二来源自动组的当前选择及目标健康状态。
7. 只修改已经定位到的层次。
8. 用目标机器自己的 Mihomo 二进制校验，重启服务后复测。

## 常见现象

| 现象 | 优先检查 |
| --- | --- |
| 域名无法解析 | 系统解析器、DNS-over-TLS 和直连 DNS |
| 国内镜像失败 | 清除错误代理变量后测试直连 |
| Google 或 GitHub TLS 中断 | 对应业务组、当前选择和组级测速 |
| Codex 断流 | 人工智能组、显式 HTTP/HTTPS/WSS 代理和真实长流 |
| Raw 正常但 clone 失败 | 区分 GitHub 主站、Raw、codeload 和 SSH 链路 |
| SSH clone 失败 | 主机密钥、公钥认证、22/443 端口，不用 HTTPS 测速代替 |

## 控制器使用原则

- 可以读取提供器、业务组和延迟历史；
- 可以触发某个 `url-test` 组的原生业务测速；
- 不用控制器把自动组固定到具体节点；
- 不在日志中打印订阅地址、节点凭据或控制器口令。

普通请求失败但代理端口正常时，先刷新对应业务组并重试一次。若同一目标在多台服务器持续失败，再判断测试目标、订阅节点或规则分类是否需要调整。

提供器能下载订阅并不表示其节点入口可达。若一个来源在多个业务、多个服务器上健康数均为 0，应先做不含凭据的节点入口 TCP 汇总。当前策略把第二来源保留在逻辑大池中，但只展开到智能和通用两个 `url-test` 组，避免全部节点在七个业务组重复展开；恢复后会在下一轮自动重新参与。

现网不设 `max-failed-times`。一次真实请求失败不会另外触发测速或逐请求故障转移；七个业务组依赖 600 秒周期，两个第二来源组依赖 1800 秒周期。
