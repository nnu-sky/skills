# 路由与节点选择

## 两层职责

网站分类与节点选择是两件事：

1. 规则决定请求进入哪个业务组；
2. 业务组用自己的目标测试候选，选择当前可达且延迟较低的线路。

分类数据可以使用 `MetaCubeX/meta-rules-dat`；自动测速和切换由 Mihomo 原生 `url-test` 完成。规则数据不会替 Mihomo 选择节点，Mihomo 也不会自行改写分类规则。

## 节点提供器

两个订阅保持物理独立，并合成为一个逻辑生产大池：

- 类型：HTTP 动态提供器；
- 资源刷新：86400 秒；
- 节点名称增加来源前缀；
- 排除剩余、流量、重置、套餐、到期、官网、公告、过滤和客服条目；
- 不限制地区；
- 不维护固定“最佳若干节点”。

第一来源的节点直接进入七个业务组，每 600 秒按业务目标测速。第二来源的完整节点池分别进入智能与通用两个原生 `url-test` 组，每 1800 秒分别用人工智能入口和通用外网入口测速，单节点超时 3000 毫秒。第二来源全部不可达时不会被业务组选中，入口恢复后会自动重新参与。订阅刷新只更新节点名单，不会重写分流规则。

不把第二来源的全部节点直接展开进七个业务组。实测 160 个失效入口直接展开会产生 `160 × 7` 次失败探测，并在首次预热期间干扰正常请求；两组方案每轮合计只展开 `160 × 2` 个候选，同时保留人工智能与通用外网的目标差异。

## 七个业务组

统一参数：

- `type: url-test`；
- `interval: 600`；
- `lazy: false`；
- `timeout: 10000`；
- `tolerance: 200`。

`tolerance: 200` 表示新候选只快不到 200 毫秒时不切换，减少延迟接近时的来回跳动。

两个第二来源组的单节点超时为 3000 毫秒，七个业务组为 10000 毫秒。不设置 `max-failed-times`，不依赖失败计数触发的额外检查；节点选择只依赖上述原生定时测速。

| 组名 | 候选 | 测试目标 |
| --- | --- | --- |
| 人工智能自动 | 第一来源全部节点＋第二来源智能自动 | Codex 模型入口，接受未授权状态 |
| 谷歌自动 | `DIRECT`＋第一来源全部节点＋第二来源通用自动 | Google `generate_204` |
| GitHub 核心自动 | `DIRECT`＋第一来源全部节点＋第二来源通用自动 | GitHub `robots.txt` |
| GitHub 内容自动 | `DIRECT`＋第一来源全部节点＋第二来源通用自动 | 小型 Raw 文件 |
| GitHub 归档自动 | `DIRECT`＋第一来源全部节点＋第二来源通用自动 | 小型真实 codeload 归档 |
| 学术外网自动 | `DIRECT`＋第一来源全部节点＋第二来源通用自动 | arXiv `robots.txt` |
| 默认外网自动 | 第一来源全部节点＋第二来源通用自动 | Cloudflare `generate_204` |

Google、GitHub 三类和学术外网保留 `DIRECT` 作为普通候选。人工智能和默认外网不包含 `DIRECT`。

## 推荐规则顺序

1. 回环、局域网、容器网络和明确内部资源直连；
2. 多出口共同验证通过的开发下载域直连；
3. 人工智能分类进入人工智能组；
4. codeload 进入 GitHub 归档组；
5. `githubusercontent.com` 进入 GitHub 内容组；
6. GitHub 主站和剩余 GitHub 分类进入核心组；
7. Google 分类进入 Google 组；
8. 境外学术分类进入学术组；
9. 中国大陆域名和 IP 直连；
10. 其余流量进入默认外网组。

规则必须从具体到宽泛。GitHub 三类应先于完整 GitHub 分类，否则 Raw 和 codeload 会被核心组提前收走。

## 开销

若第一来源有 `N` 个候选，七组每十分钟的理论探测量约为 `7N` 次，另加第二来源的两个目标全量测试和少量自动线路、`DIRECT` 测试。探测不调用模型、不消耗模型令牌、不占 GPU，但会消耗代理流量、TLS 握手、少量 CPU 和连接资源。

当前第一来源约 55 个节点按七个目标每 600 秒检测，第二来源约 160 个节点按两个目标每 1800 秒检测；四出口每天理论约 29 万次轻量探测。不增加额外切换守护或长期监控。
