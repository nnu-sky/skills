# 直连与自动代理测试证据

采样方式：四个独立服务器出口，对五个轻量目标各执行一次直连和一次当前 Mihomo 自动代理请求。状态 `000` 表示该次请求未获得 HTTP 响应，不区分连接超时、TLS 中断或远端提前关闭。

这是早期单次快照，只用于调整候选结构，不代表永久可用率。后续时间序列证据见下文。

## 汇总

| 目标 | 直连成功 | 自动代理成功 | 当前建议 |
| --- | ---: | ---: | --- |
| Google `generate_204` | 0/4 | 3/4 | 早期快照倾向代理；现行方案仍保留 `DIRECT` 参与实测 |
| GitHub 主站 | 0/4 | 3/4 | 早期快照倾向代理；后续时间序列支持保留 `DIRECT` |
| GitHub Raw | 4/4 | 4/4 | 保留 `DIRECT`＋代理比较 |
| GitHub codeload | 4/4 | 4/4 | 保留 `DIRECT`＋代理比较 |
| arXiv | 4/4 | 4/4 | 保留 `DIRECT`＋代理比较 |

## 如何使用这些结果

- 这次早期快照曾不支持 Google 和 GitHub 主站的直连候选；后续时间序列已经改变 GitHub 主站结论。
- Raw、codeload 和 arXiv 不应固定代理；四个出口的直连都成功，保留比较可以减少代理流量。
- 某一出口单次代理失败不应触发整套回滚。先刷新对应业务组并重试一次。
- 若要改变候选结构，应在不同时间至少再采样一轮，并记录 HTTP 状态，而不是只比较 ICMP 或 TCP 延迟。

## 12 个时间点补充证据

2026-08-06 至 2026-08-07 的观察提前结束于 12 个时间点，共保留四台服务器 48 条有效记录。采集、服务、端口和服务进程均无异常，但业务请求存在约 5 秒的 TLS 握手中断。

- GitHub 主站直连成功 31/48；
- GitHub 主站自动代理成功 40/48；
- 两路至少一路成功 45/48；
- 其中 5 次只有直连成功，14 次只有代理成功。

因此 GitHub 核心组重新加入 `DIRECT`，由 Mihomo 按主站目标在直连与当前已验证代理来源之间选择。Google 直连同期为 0/48；现行简化方案仍保留 `DIRECT` 作为可测候选，但应预期原生测速通常选择代理。

## 提供器可达性补充

后续四台运行态显示，来源一在七类业务中存在 15–46 个健康候选，来源二已经完成的业务健康数均为 0。单台服务器对缓存节点入口做不含凭据的 TCP 汇总：来源一 51 个唯一入口有 50 个可达，来源二 162 个唯一入口为 0 个可达。

来源二的订阅仍有效，因此保留在逻辑生产大池中，但完整节点池只展开到智能与通用两个 1800 秒原生组。当前全部失败时不会被业务组选择，入口恢复后可自动重新参与；这把每轮 1120 个第二来源候选降为 320 个，同时保留两种目标差异。

历史连续失败复测中，`max-failed-times: 1` 在一个出口触发了原生健康检查，但另一个出口的同类 AnyTLS 超时没有触发。因行为不一致，现行简化方案已删除该字段，生产业务组只依赖 600 秒原生周期。
