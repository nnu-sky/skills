# 可选的静默观察

## 目的

一次成功只能证明当时可用。本方案只在确有时间变化问题时启用，不作为每次配置变更的验收要求；发现系统性失败后应停止采样并进入根因诊断。若运行满 24 小时，可覆盖一次每日订阅刷新和 144 次十分钟业务测速。

## 采样频率

- 启动时采样一次；
- 之后每小时采样一次；
- 24 小时末采集最终样本；
- 合计 25 个时间点。

## 每次采集

1. Mihomo 服务和三个本地端口状态；
2. 两个提供器的类型、节点数、存活数和信息条目数；
3. 七个业务组和两个第二来源自动组的当前来源及所选节点不可逆匿名指纹，不记录具体节点名称；
4. Google、GitHub 主站、Raw、codeload、arXiv 的直连与代理状态和耗时；
5. 人工智能与默认外网的代理状态；
6. 最近 65 分钟服务日志中的错误、超时和 TLS 关键词数量；相邻窗口有 5 分钟重叠，只报告单窗口范围，不累加为独立事件；
7. 服务进程是否在观察期间发生重启。

每个时间点每台执行 12 个未认证轻量 HTTP 请求，四台完整观察约 1200 次；不运行真实 Codex，不消耗模型令牌。远程采样失败应单独计数，不能冒充有效样本。

## 最终汇总

- 每台机器、每个目标的成功率；
- 直连与代理的成功率和耗时中位数；
- 每个业务组的匿名节点切换次数与来源切换次数；
- provider 节点数、存活数和刷新次数变化；
- 服务重启、端口消失和日志异常时段；
- 是否支持继续保持当前候选结构。

## 判断建议

- Google 代理成功率低于 95%：优先检查测试目标与代理节点质量，不因代理失败直接加入不可达的直连。
- GitHub 主站分别比较直连与代理；若两路存在互补成功，保留 `DIRECT` 作为普通自动候选。
- Raw、codeload 或 arXiv 直连成功率低于 95%、代理明显更稳：再考虑移除对应组的 `DIRECT`。
- provider 节点数变化但七组持续成功：属于正常订阅刷新。
- 单次失败随后一小时恢复：记录为瞬态，不自动回滚。
- 连续两次以上失败或服务端口消失：进入人工诊断。
